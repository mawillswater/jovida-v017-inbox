SECTION A

Live Activity · 推送 当下最该做的 Action Now

本期 Live Activity 的唯一职责是在锁屏 / 灵动岛上呈现"用户当下最该做的事"。 没有合适的 Action Now 时，LA 主动消失——不做装饰性占位、不做心情语 / 鼓励语 / 元数据陈列。 "知道什么时候该消失"是陪伴感的关键素养。

A1 · 设计原则与硬约束

📘 必做的 4 个位置（Apple ActivityKit 规范要求）
  • Lock Screen 卡片 · 用户解锁前抬眼看到的主战场
  • Dynamic Island · Compact（默认胶囊态）· 任何 app 顶部一直可见
  • Dynamic Island · Minimal（多 LA 共存时压缩态）· 极小圆点
  • Dynamic Island · Expanded（启动 / Alert / 长按时展开）· 大卡片
  • API 上 ActivityConfiguration 的 dynamicIsland 闭包要求 4 态全交付，无法只挑其中几个
⚠️ 资源体积硬上限 · 静态 + 动态各 < 4 KB
  • ActivityAttributes（静态资源，启动时一次性传入）：≤ 4 KB · 包含 Jovida 角色 ID、模板 token 等不变信息
  • ContentState（动态资源，每次 update 携带）：≤ 4 KB · 包含 Action 标题 / 副标题 / emoji 标识
  • 4 KB 装不下任何图片二进制——所有 Jovida 角色图、Action 配图必须预打包在 app bundle，ContentState 只传"asset 名"字符串
  • 所以 backend 推过来的字段必须是引用（character_pose=happy / action_emoji=skincare），不是 url
⛔ MVP 严格不做
  • 不放任何按钮（无论锁屏卡 / 灵动岛 expanded）· 整体 tap 跳 Action 详情页，简化心智
  • 不做"鼓励语 / 心情语 / 装饰态" LA · 没合适 Action 就让 LA 消失
  • 不做 LA 内的填表 / 评论 / 复杂交互 · LA 只是入口
  • 不做高频更新 · 心跳节奏由 Agent 决定（一般一天 2-4 次内容切换），中间静默

A2 · 各位置展示字段（精确 spec）

下表是每个位置 LA 视图能且仅能拿到的字段。设计稿和工程都按这张表交付。

Lock Screen 卡片
① Jovida Character 图（asset，~36×36pt 头像）
② Action emoji / 图（asset，~34×34pt 方框）
③ Action 标题（一行，最多 ~14 字）
④ Action 副标题（一行，最多 ~24 字）
DI · Expanded
同 Lock Screen（IP + emoji + 标题 + 副标题）
视觉布局压缩为更紧凑的胶囊形态，~208pt 宽，~80pt 高
DI · Compact
Leading：Jovida Character 图（圆形头像，~24×24pt）
Trailing：Action emoji 或 1-2 字符状态（~13px 字 / ~24×24pt 图）
中间是摄像头胶囊区，不能放任何内容
DI · Minimal
Jovida Character 图（单个圆形 dot，~18×18pt）
多 LA 共存时被压缩到此态，仅作"我还在"的提示，无任何文字
点击行为（4 态共通）
整体 tap → Action 详情页（带 Action ID 的 deep link）
Action 详情页是 app 内单条 Action 的完整视图（含一键完成、snooze、相关聊天上下文）

A5 · Backend 生命周期 · 创建 / 更新 / 消失

三段逻辑由 Agent + 推送服务共同负责。

CREATE · 创建

用户打开 App 时

  • 用户每次冷启 / 切回前台时，Agent 立即评估"当下最该做的 Action Now"
  • 有合适 Action 时调 Activity.request(...) 创建 LA
  • 同时拿到 push token + push-to-start token，立即上报后端存档
  • 无合适 Action 时不创建（也不假装创建）
UPDATE · 心跳更新

Action Now 内容变化时

  • Agent 按心跳节奏（典型一天 2-4 次）评估 Action Now 是否需切换
  • 需切换时，服务端通过 APNs 向 LA 的 push token 推 ContentState（≤4KB）
  • 切到完全不同事件用 alert update（灵动岛展开 ~4s + 横幅 + 触觉 + 声音）
  • 同事件内进度变化用静默 update（无 alert）· 内容偷偷换
END · 消失

三种触发条件

  • Agent 判无合适 Action Now → 服务端推 end，LA 主动消失
  • 超 8h 时长上限 → 系统强制 end（再 stale 4h 后从锁屏移除）
  • 用户左/右滑关闭 → 视觉 dismiss，App 不立即重启（视为弱负反馈）
💰 成本节约规则
  • 超 8h 后 Agent 不再评估 / 不再推送——因为系统强制 end 了，再算白搭
  • 只在用户下次打开 App 时重启 Agent 评估循环（拿到新 push token，进入新 8h 窗口）
  • iOS 17.2+ 用户可启用 push-to-start token：服务端在用户没打开 App 时仍能远程拉起新 LA（接力陪伴）。但要遵守每天 alert ≤ 2-3 次的 HIG 上限
  • "超 8h 仍生成 Action Now 候选"是无效计算，应直接跳过——这是 Agent 队列的硬过滤条件

SECTION D

SECTION E

Agent / 后端 · 资源记忆机制

核心原则：用户导入的资源要被很好地存住，不能淹没在 history 长河里——但不应该专门开一个新字段 / 表来存"资源"。 正确的做法是用 Agent 已有的记忆机制（memory） 承载资源关联，让资源天然成为某个 desire 的一部分。

E1 · 例子 · 长程任务的资源化

E1·1100 个新闻链接 · 分 3 个月读完

用户：在多个 session 里分批向 Jovida 发了 100 个 AI 监管类新闻链接。最近一次说"这些分 3 个月帮我读完"。

# 期望的 Agent 行为
memory:
  desire: ai_regulation_reading
  resources:
    - 100 个 链接（哪天来 / 哪个 session）
    - 用户的指令："3 个月慢读"
  deduced_plan:
    - 每天读 ~1.1 个，分类滚动
    - 进度跟踪挂在 desire 上
    - LA Action Now 偶尔变 "今天读这一篇"

关键：100 个链接不是 100 条 inbox 待办，而是同一个 desire 下的资源池。Agent 推理出节奏 + 顺序，每天主动选一篇推到 LA。

E1·2YouTube 视频迭代已有 desire

用户：传一个 YouTube 视频链接（讲睡眠科学），说"用这个指导我睡觉变好"。已有 desire：「规律作息修复」。

# 期望的 Agent 行为
memory:
  desire: sleep_improvement
  resources:
    - "YouTube/sleep-science" 视频
    - 用户意图："用它指导睡觉"
  action:
    - 自动转写视频要点
    - 把要点融入 desire 的执行计划
    - 之后的 action now 引用其中片段
    - 例：21:30 LA = "今天试视频里的 4-7-8 呼吸法"

关键：资源不是孤立条目，融入既有 desire 改写它的执行计划，让 desire 更具体、更个性化。

E2 · 实现 · 用 memory 不用专字段

设计取舍
资源的生命周期是 desire 的子集。
所以不开 "resources" 表 / 字段，而是把每个资源作为 memory 节点挂在 desire 下：
  • 新建资源 → 写入 memory：desire_id + resource_descriptor + user_intent + timestamp
  • 查询资源 → 在 desire 视图下检索该 desire 的 memory 节点子集
  • 资源消费 → 写入 consumption memory（"已读 / 已用 / 已转化为 action"），形成进度
  • 跨 desire 资源 → 同一个资源 id 可被多个 desire 引用（不复制内容，只多一条 memory link）
📐 为什么不专门开字段
  • 资源天然有"主体"——它属于某个 desire（或要变成新 desire）。把它和 desire 绑在一起才有意义。
  • 专开字段会让资源变成"另一个收件箱"——用户进来翻一遍，毫无目的。我们要的是"资源服务于目标"。
  • memory 机制本来就是为长程相关性设计的——存 100 个链接、跨 3 个月引用，不需要新基建。
  • 暂存夹是UI 概念（未归类资源的过渡视图），不应该是数据存储层。两者分离。
